# CheckStock — где сейчас товар?

Веб-прототип учёта остатков по складам фулфилмента (ФФ). Менеджер видит по
каждому артикулу: сколько физически лежит на каждом ФФ, сколько доступно,
сколько в резерве FBS и сколько уже отправлено — между ФФ, на склад
маркетплейса по FBO и клиенту по FBS.

Стек: **Python 3.13, FastAPI, PostgreSQL 17**, SQLAlchemy Core + asyncpg,
Alembic. Интерфейс — React + TypeScript + Vite.

## Запуск

Нужен только Docker.

```bash
docker compose up --build
```

- Интерфейс: <http://localhost:8080>
- Документация API (Swagger): <http://localhost:8080/api/docs>

При старте применяются миграции и загружаются тестовые данные из задания:
один магазин, ФФ «Север» и «Юг», три товара и тестовый приход (он проведён
обычной операцией прихода и виден в истории). Повторный запуск данные не
дублирует.

Начать с чистой базы: `make reset`.

### Настройки: база и порты

Файл `.env` для запуска не нужен — всё работает со значениями по умолчанию.
Они описаны в [`.env.example`](.env.example); чтобы изменить порт или
учётные данные, скопируйте его в `.env` и поправьте.

Проект — три отдельных контейнера (`docker compose ps` покажет все три):
интерфейс, бэкенд и база. Бэкенд — самостоятельный сервис FastAPI; nginx
в контейнере `web` только пересылает ему запросы `/api`.

| Сервис | Что это | Адрес на вашей машине | Переменная |
|---|---|---|---|
| `web` | интерфейс (nginx раздаёт React и проксирует `/api`) | <http://localhost:8080> | `WEB_PORT` |
| `api` | FastAPI; Swagger на `/api/docs` | через `web`: <http://localhost:8080/api/> | — |
| `db` | PostgreSQL 17 | `localhost:5433` | `DB_PORT` |

База: `checkstock`, пользователь `checkstock`, пароль `checkstock`
(`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`). Данные лежат в томе
Docker `db-data` и переживают перезапуск; `make reset` их стирает.

Порт базы снаружи — 5433, а не обычный 5432, чтобы не столкнуться с
PostgreSQL, уже установленной на машине. Подключиться и посмотреть таблицы:

```bash
docker compose exec db psql -U checkstock checkstock
```

У API своего порта наружу нет: и интерфейс, и API, и Swagger открываются с
одного адреса, так что запуску могут помешать только два порта — 8080 и
5433. Если один из них занят, достаточно переменной:
`WEB_PORT=9090 docker compose up --build`.

## Проверки

```bash
make test        # 69 тестов: правила домена + сквозные сценарии на PostgreSQL
make check-arch  # границы слоёв (import-linter)
make lint        # ruff
```

Без `make` то же самое: `docker compose run --rm api pytest` (и `ruff check .`,
`lint-imports` вместо `pytest`).

Сквозные тесты идут через HTTP на **настоящей PostgreSQL**, без подмены
базы: блокировки строк, CHECK-ограничения и транзакции — часть проверяемого
поведения. После **каждого** изменяющего запроса тестовая обвязка
(`backend/tests/e2e/harness.py`) запускает сверку журнала с остатками, так
что требование «остатки сходятся после каждого действия» проверяется
буквально.

| Что проверяется | Файл |
|---|---|
| Приход, перемещение, FBS, FBO, приёмка | `tests/e2e/test_accounting_flow.py` |
| Нехватка на выбранном ФФ при достаточном общем остатке | `tests/e2e/test_shortage.py` |
| Удаление ФФ с остатком | `tests/e2e/test_warehouse_deletion.py` |
| Повторное подтверждение, ключи идемпотентности, параллельные запросы | `tests/e2e/test_repeated_confirmation.py` |
| Правила остатка и переходы статусов (без базы) | `tests/domain/` |

### Проверить руками за пять минут

1. **Остатки.** На главном экране — таблица из задания: SKU-101 10/6,
   SKU-102 5/0, SKU-103 0/4.
2. **Нехватка.** «Резерв FBS» → SKU-102, ФФ «Юг», 3 шт. На Юге товара нет, на
   Севере 5. Система отказывает и показывает, где товар есть, с двумя
   выходами: оформить на Севере или переместить на Юг.
3. **Перемещение.** Нажмите «Переместить на «Юг»» → «Отправить». На экране
   остатков 3 шт. в колонке «Между ФФ»: с Севера ушли, на Юг ещё не пришли.
4. **Повторное подтверждение.** «Отправки и перемещения» → дважды быстро
   нажмите «Принять на «Юг»». В истории одна запись приёмки, на Юге 3 шт.
5. **FBS.** Зарезервируйте 3 шт. SKU-102 на Юге: физически 3, доступно 0,
   резерв 3. «Отправить клиенту» — товар уходит в «FBS → клиент».
6. **FBO.** «Отправка FBO» → SKU-101, Север, 4 шт. Товар покидает ФФ и
   числится в «FBO → склад МП», пока не нажато «Принято складом МП».
7. **Удаление ФФ.** «Склады ФФ» → удалить «Юг». Диалог показывает, сколько
   на нём числится. После удаления склад остаётся в таблице остатков с меткой
   «удалён», история цела, а новый резерв на нём недоступен.
8. **Сверка.** Значок «Учёт сходится с журналом» в шапке — результат
   `GET /api/reconciliation`.

## Ключевые решения

### 1. Журнал движений — источник правды, таблица остатков — его проекция

Каждая операция пишет в `movements` строку «перенесли N штук со счёта A на
счёт B». Это двойная запись: товар не появляется и не исчезает, он
переходит между счетами.

| Счёт | Что это |
|---|---|
| `supplier` | поставщик (внешний источник прихода) |
| `warehouse_available` | на ФФ, доступно |
| `warehouse_reserved` | на ФФ, в резерве FBS |
| `transit_transfer` | в пути между ФФ |
| `transit_fbo` | в пути на склад маркетплейса |
| `marketplace` | принято складом маркетплейса |
| `transit_fbs` | в пути к клиенту |

Резерв FBS — тоже перенос: с «доступно» на «в резерве» того же склада.
Поэтому история показывает резерв отдельной операцией, а «доступно» не
нужно хранить отдельным числом.

Таблица `stock (товар, ФФ → on_hand, reserved)` нужна, чтобы быстро читать
остаток и блокировать строку. Она меняется в той же транзакции, что и
журнал. **Сверка** (`GET /api/reconciliation`) пересчитывает все счета из
журнала и сравнивает с `stock` и с документами в пути. Любое расхождение
означает, что остаток изменили мимо журнала.

*Почему не только журнал:* пришлось бы суммировать историю при каждой
проверке «хватает ли» и не было бы строки, которую можно заблокировать.
*Почему не только таблица остатков:* не было бы ни истории, ни способа
доказать, что цифры верны.

### 2. Одна операция — одна транзакция с блокировкой строки остатка

Обработчик открывает транзакцию, читает строку остатка через
`SELECT … FOR UPDATE`, проверяет правило в доменном объекте, пишет остаток,
документ и журнал — и фиксирует всё вместе. Два параллельных резерва
последней единицы выстраиваются в очередь: второй увидит уже уменьшенный
остаток и получит отказ.

Последний рубеж — CHECK-ограничения в PostgreSQL (`on_hand >= 0`,
`0 <= reserved <= on_hand`). Даже при ошибке в коде база не запишет
отрицательный остаток.

Тест `it_never_reserves_more_than_is_available` шлёт 12 одновременных
заказов на 5 единиц и проверяет, что прошло ровно 5.

### 3. Повторное подтверждение: конечный автомат + ключ идемпотентности

Два разных случая — два механизма.

**Подтверждение существующего документа** (принять перемещение, отправить
или отменить FBS, принять FBO). Документ — конечный автомат. Обработчик
блокирует строку документа; метод перехода возвращает `True`, только если
переход случился сейчас. При повторе он возвращает `False`, остатки не
трогаются, клиент получает тот же ответ `200`. Противоположное решение
(отправить отменённый заказ) — ошибка `409`.

**Создание документа** (приход, отправка перемещения, резерв FBS, отправка
FBO). У документа ещё нет идентификатора, поэтому клиент присылает заголовок
`Idempotency-Key`. Ключ записывается в той же транзакции, что и операция.
Повтор с тем же ключом возвращает уже созданный документ. Тот же ключ с
другими параметрами — `409`. Если операция упала, ключ откатывается вместе с
ней, и запрос можно повторить. Интерфейс генерирует ключ на каждый набор
полей формы, так что двойной клик не создаёт два прихода.

### 4. Нехватка: отказ с подсказкой, без автоматического дробления

Если на выбранном ФФ доступного товара меньше, чем запрошено, операция
отклоняется целиком (`409 insufficient_stock`) и ничего не меняет. В ответе —
сколько запрошено, сколько доступно здесь и на каких действующих ФФ товар
есть. Интерфейс предлагает два выхода: оформить на другом ФФ или переместить
недостающее.

*Почему система не берёт товар с другого склада сама:* выбор склада —
решение менеджера. От него зависят сроки и стоимость доставки, а
перемещение между ФФ занимает время. Молчаливое списание с другого склада
дало бы остатки, которые сходятся на бумаге, но не совпадают с тем, что
человек собирался сделать.

Доступным считается только свободный остаток: зарезервированный под FBS
товар нельзя ни переместить, ни отправить по FBO.

### 5. Удаление ФФ — архив, а не DELETE

У склада проставляется `deleted_at`, строка остаётся. Остатки, документы и
журнал ссылаются на неё внешними ключами, поэтому ничего не теряется, а
товар продолжает числиться на удалённом складе — это видно на экране
остатков (метка «удалён») и на экране складов.

| На удалённом ФФ | Можно? | Почему |
|---|---|---|
| Приход, перемещение *на* него | нет | склад закрыт |
| Новый резерв FBS, отправка FBO | нет | нельзя обещать товар с закрытого склада |
| Перемещение *с* него | да | иначе остаток застрял бы навсегда |
| Отправить или отменить уже оформленный заказ FBS | да | обязательство возникло до удаления |
| Принять перемещение, которое уже ехало | да | иначе товар повис бы в пути |

Остаток удалённого ФФ входит в «физически всего», но не входит в «доступно
всего» и не предлагается при нехватке. Когда на удалённом складе не остаётся
товара, он исчезает с экрана остатков, но остаётся в истории. Название
уникально только среди действующих ФФ (частичный уникальный индекс), так что
новый «Юг» завести можно.

### 6. Архитектура: порты и адаптеры, зависимости внутрь

```
backend/app/
  domain/          правила учёта на чистом Python: остаток, документы, журнал, порты
  application/     операции (commands.py) и чтение со сверкой (queries.py)
  infrastructure/  PostgreSQL: unit of work, репозитории, SQL для чтения
  api/             FastAPI: маршруты, схемы, перевод ошибок в HTTP
  main.py          точка сборки
```

Правила учёта не зависят от FastAPI и SQLAlchemy, поэтому проверяются
тестами без базы за доли секунды. Границу слоёв проверяет `import-linter`
(`make check-arch`), а не договорённость.

Для прототипа из одной предметной области это один модуль без шины событий
и без отдельного файла на каждую команду — такая обвязка здесь была бы
шаблонным кодом.

### 7. Согласованное чтение

Экран остатков и сверка собираются из нескольких запросов. Они выполняются
в одной транзакции `REPEATABLE READ`, то есть видят базу на один момент
времени. Это не перестраховка: параллельный тест поймал случай, когда
сверка читала журнал и остатки в разные моменты и показывала ложное
расхождение при верном учёте.

## Допущения и границы прототипа

- **Перемещение принимается целиком.** Частичной приёмки и расхождений при
  приёмке нет.
- **FBS после отправки остаётся «в пути к клиенту».** Шагов «доставлен» и
  «возврат» нет — задание заканчивается на отправке.
- **Один товар в документе.** Заказ, перемещение и поставка — на один
  артикул.
- **Товары — из тестовых данных.** Интерфейса для создания товаров нет.
- **Один магазин.** В схеме есть `shops` и `products.shop_id`, чтобы
  несколько кабинетов не потребовали переделки, но переключения магазинов
  в интерфейсе нет.
- **Без авторизации и ролей.**
- **Удалённый ФФ нельзя восстановить** из интерфейса.

## Как использовался ИИ

Код написан с помощью Claude Code. За мной оставались решения из раздела
выше — модель учёта, поведение при нехватке и при удалении ФФ, механизм
идемпотентности — и проверка результата.

Где ИИ ускорил работу: каркас проекта, SQL и репозитории, интерфейс, тексты
тестовых сценариев.

Как проверялся результат:

- **Сверка после каждого действия.** Каждый сквозной тест после каждого
  запроса сверяет журнал с остатками.
- **Намеренные поломки.** Убрал `FOR UPDATE` со строки остатка —
  параллельный тест упал. Отключил проверку «уже отправлен» — упал тест
  повторного подтверждения. Значит, тесты действительно ловят эти ошибки, а
  не проходят всегда.
- **Найденная проблема.** Параллельный тест показал ложное расхождение при
  сверке: журнал и остатки читались в разные моменты времени. Исправлено
  чтением в одном снимке (решение 7).
- **Сценарии руками в браузере**: нехватка, двойное нажатие подтверждения,
  удаление ФФ с остатком.
- **Границы слоёв** проверяются автоматически (`make check-arch`).

Правила для ИИ-агента лежат в `CLAUDE.md` и `.claude/`: описание
архитектуры, правила учёта и хук, который не даёт записать импорт,
нарушающий границы слоёв.

## Локальная разработка без Docker

Нужны Python 3.13, Node 22 и PostgreSQL. Базу проще взять из Compose
(`docker compose up -d db`) — под неё и написан `backend/.env.example`.
Интерфейс в режиме разработки шлёт `/api` на `http://localhost:8000`;
другой адрес задаётся переменной `API_TARGET`.

```bash
# бэкенд
cd backend
python3.13 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
cp .env.example .env            # строка подключения; описание — внутри файла
.venv/bin/alembic upgrade head && .venv/bin/python -m app.seed
.venv/bin/uvicorn app.main:app --reload

# интерфейс (в другом терминале)
cd frontend
npm install && npm run dev      # http://localhost:5180
```

Тесты локально: `cd backend && .venv/bin/pytest` — создают отдельную базу
`checkstock_test`.
